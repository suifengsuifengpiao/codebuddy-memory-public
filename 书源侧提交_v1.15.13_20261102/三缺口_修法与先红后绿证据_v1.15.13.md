## 一、缺口 1 · R6 漏掉默认路径

**根因**：`check_search` 里 R6 整段嵌在 `if opt:` 分支内。`searchUrl` 不写选项（= 宿主默认 GET）走 `else`，只打一条 NOTE，**最常命中的提示在最常见的写法上不响**。

**修法**：`opt is None` 时把 `method` 定为 `GET` 后继续往下走，R6 移出分支；`method` 显式 `POST` 仍不报（关键词走 body）。

### 证据

先红（v1.15.12 基线闸，夹具 `/tmp/t_A.json`：`{"searchUrl":"https://a.com/s?q={{key}}"}`）

```
[NOTE ] R4 searchUrl 无选项（默认 GET）
小计：ERROR=0  WARN=0  NOTE=2      ← 该响的不响
```

同夹具显式 `method:GET`（证明"只有裸写法漏"，不是 R6 整体坏了）

```
[WARN ] R6 GET URL 含 {{key}}：…建议 {{java.encodeURI(key)}} 或实测确认
小计：ERROR=0  WARN=1  NOTE=2
```

后绿

```
[WARN ] R6 GET URL 含 {{key}}：…
[NOTE ] R4 searchUrl 无选项 → 按默认 method=GET, webView=False 检查
小计：ERROR=0  WARN=1  NOTE=2      ← WARN 0→1
```

因果复现（把 `opt and` 塞回条件，其余一字不动）

```
小计：ERROR=0  WARN=0  NOTE=2      ← 重新变回 0
```

控制格：显式 `method:POST`（body 带 `{{key}}`）→ `WARN=0`；POST 且 URL 也带 `{{key}}` 双写 → `WARN=0`（`grep -c R6` = 0）。

## 二、缺口 2 · `--strict` 空参数

**根因**：`grep strict` 只命中 31 行（docstring 用法）与 206 行（报错用法文本），**没有任何分支读它**。传了等于没传。

**修法（主灵定：实现而非删用法行）**：`strict = "--strict" in sys.argv[1:]`；无 ERROR 但有 WARN 时 `exit 1`，并输出「--strict: WARN 视为失败」。无 WARN 照常 `exit 0`；有 ERROR 时 ERROR 口径优先。

### 证据

先红

```
$ python3 check_request_layer.py /tmp/t_A.json --strict
结论：请求层通过（ERROR=0）。
exit=0                             ← 带了 --strict 也照样通过
```

后绿

```
结论：--strict: WARN 视为失败，请求层不通过（WARN=1）。去掉 --strict 则判通过——WARN 是
「可能有问题、需实测确认」，严格模式要求先确认再交付。
exit=1
```

因果复现（`if strict and total_warn:` → `if False and strict and total_warn:`）

```
回退版 exit=0
修复版 exit=1
```

边界两格

| 情形 | 夹具 | 期望 | 实测 |
|---|---|---|---|
| 零 WARN + `--strict` | `?q={{java.encodeURI(key)}}` | exit=0 | **exit=0** |
| 有 ERROR + `--strict` | 事故标本 | exit=1 且报 ERROR=4（不被 strict 掩盖） | **exit=1，ERROR=4** |

> 副作用修正：原「通过」分支会复述「（--strict 口径：WARN 亦视为失败）」，导致短路版与正常版日志**几乎一样**、只能靠 exit code 分辨。已删——现在日志与退出码同向。

## 四、（新发现）切分算法与宿主不一致

**怎么发现的**：接上缺口 3 的通道之后跑一遍全量 corpus，八叉书库 ERROR=2、luyouxs ERROR=1、手机小说 ERROR=1——**这三本都是已交付且真机通过的**。三份错报全指向 `split_options`。

**核到哪一层**：不是猜，读 3.25 dex 的 `io.legado.app.model.analyzeRule.AnalyzeUrl`：

- `<clinit>`：`paramPattern = Pattern.compile("\\s*,\\s*(?=\\{)")`
- `analyzeUrl()`：`matcher.find()` 命中则 `url = substring(0, start)`、`选项 = substring(end)`，交 gson `fromJson(UrlOption.class)`；**未命中则整串当 url、默认选项**；解析异常被 `runCatching` 吞成 null → 按默认选项继续（**不崩**）
- `initUrl()` 调用序：`analyzeJs()` → `replaceKeyPageJs()` → `analyzeUrl()`

旧实现是 `rfind(",{")` + `json.loads(整段后缀)` —— 比宿主**两头都严**：找的是最后一个切分点（宿主找第一个），且要求整个后缀都是合法 JSON（宿主解析完一个对象就停）。

**用真 gson 复核**（`java_probe/`，gson-2.13.2）：八叉书库的 exploreUrl 交 gson → `[OK] 元素数=15`；其 searchUrl 尾部对象交 gson → 只读出 `{"accept":…}` 这个对象即返回，后面的 JS 源码不参与。

**修法与效果**（12 本前後对照，见 `corpus_full_regression.txt`）

| 书源 | v1.15.12 | v1.15.13 | 说明 |
|---|---|---|---|
| 八叉书库 | **ERROR=2** | ERROR=0 | exploreUrl 内嵌 `{{多行 JS}}`（Python json 报裸回车错、gson 能过）+ searchUrl `@js:` 尾部对象 |
| luyouxs | **ERROR=1** | ERROR=0 | `<js>` 形态，关键词以 `+key+` 拼接，原判「无 {{key}}」 |
| 手机小说 | ERROR=1 | ERROR=1 | 尾部对象是**真选项**，宿主解析失败后降级默认 GET（不崩），保留 ERROR，见未验边界 |
| 另 9 本 | — | 逐本不变 | 含 bimidu +1 WARN（见下） |

顺带修的 R4 关键词载体误判：`{{java.encodeURI(key)}}` 是 R6 自己给的处方，原逻辑却把它判成「没有 {{key}}」→ ERROR，等于**照建议改完反被罚**。改为「url 段或 body 里出现 key 变量即算」。边界格：

```
?q=abc                     → ERROR（真没搜索词，必须报）
/monkey?s={{k}}            → ERROR（词边界生效，"monkey" 不算 key）
?q={{java.encodeURI(key)}} → 0（处方写法放行）
body="q={{java.encodeURI(key)}}"（POST）→ 0
```

唯一新增告警：bimidu `WARN 4→5`。其 `searchUrl` **没有 `method` 键**（选项只有 `charset`），即宿主默认 GET —— 新判据命中是**正确行为**，不是误报。

## 八、未验边界（照实写，不含糊）

1. **手机小说 `<js>` 尾部 `{"js":…}` 该判 ERROR 还是 NOTE 未定**。按 dex，宿主会把它当选项、解析失败后 `runCatching` 吞掉并降级默认 GET —— 即**不崩但静默降级**。保留 ERROR 的理由：与 duomle R4 同族（选项写法有真实后果），且它是已交付书源，改判定会改变既有结论，需真机复核后再定。
2. **gson 版本**：`exploreUrl` 数组内嵌 `{{ }}` 的宽容度是在 gson-2.13 上实测的，未在 3.25 内置的那版 gson 上复验。dex 证据只证明"宿主用 gson fromJson"，没证明"内置版本与本机同行为"。
3. **未跑真机**：本轮全部结论来自本地闸 + dex + 真 gson，没有一次真机搜索/发现页验证。
4. **新增判定对老书源的影响只覆盖了 12 本**（`/workspace` 10 本 + corpus 2 本），未覆盖全量在售书源。
